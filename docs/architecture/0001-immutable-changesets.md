# ADR 0001: Immutable changesets as the source-control authority

Status: Accepted for foundation rollout

## Decision

DevHub owns source-control state in PostgreSQL, independent of a hosted Git repository. An immutable changeset is the canonical contribution primitive. It identifies a content-addressed tree, zero or more ordered parents, an ordered list of typed file operations, the submitting actor and a message. A changeset may exist without creating or changing a branch. Names such as `main` are **optional references** to changeset IDs, not changesets themselves.

The existing Next.js application, Prisma/PostgreSQL persistence, Redis/BullMQ processing and contribution inbox remain in place. Existing pull-request ingestion is isolated behind `src/source-control/compatibility.ts` to preserve current clients during a future migration. The old merge endpoint continues to fail closed; an integrity-only validation is not equivalent to a successful execution/build or code-review verdict.

## Component boundaries

| Boundary | Concrete implementation | Responsibility |
| --- | --- | --- |
| Versioned API | `src/app/api/v1/repositories/[id]` | Authenticated changeset/object/reference endpoints; typed inputs and explicit errors |
| Source-control service | `src/source-control/service.ts` | Transactional changeset creation, policy enforcement, reference generation CAS, audit |
| Changeset and object storage | `SourceChangeset`, `SourceChangesetParent`, `SourceFileOperation`, `SourceObject` | Immutable DAG, file operations, canonical tree manifests and content blobs |
| Reference manager | `SourceReference` | Atomic, scoped compare-and-swap reference moves without locking contribution creation |
| Derived metadata and review | `src/source-control/derived.ts`, `SourceValidation`, `SourceChangeApproval` | Path-based assessment, persistent integrity check, human-only approval |
| Workspace client | `src/source-control/workspace-client.ts` | Typed client for object/changeset reads, submissions and conditional reference updates |
| User interface | `src/app/repositories/[id]/source` | Readable immutable history, owner approvals and reference management |
| Background orchestration | `src/workers`, `QueueJob`, `OutboxEvent` | Existing durable PR ingress, dispatch and retries; later executable source-validation jobs belong here |
| Compatibility | `src/source-control/compatibility.ts` | Preserve old PR ingestion without making external commits authoritative |

## Identity, integrity and ordering

- `Repository.id`: UUID generated by the server and scoped to its owner.
- `SourceObject.id`: 64-character lowercase SHA-256 over `kind + NUL + raw bytes`. Object payloads reside in PostgreSQL `BYTEA`. BLOB and TREE objects have separate hash domains.
- `TREE`: canonical UTF-8 JSON list of `{path,objectId}`, sorted by path, with unique, normalized relative paths. Each entry points to the byte identity of an immutable BLOB.
- `SourceChangeset.id`: SHA-256 of the canonical v1 descriptor containing repository ID, ordered parent IDs, tree ID, actor ID, message and typed file operations. Replaying the same request returns the same ID. Changesets and parent/operation rows cannot be updated after creation, enforced by PostgreSQL triggers.
- `SourceChangesetParent.position`: the ordered ancestry relationship. The *first* parent supplies the base tree for operation application. Additional parents record provenance, but **no conflict resolution or automatic merge is claimed**; clients must supply the resolved file operations explicitly.
- `SourceReference`: keyed by repository ID and name, referencing a changeset and an integer generation. The caller supplies its expected generation, or `null` for create-only. An update uses a conditional SQL update that changes exactly one matching generation; otherwise returns HTTP 409.
- All file operation payloads and tree identities are validated server-side in the same database transaction. No global repository lock is taken when creating a changeset.

## API version 1

All endpoints below are relative to `/api/v1/repositories/{repositoryId}`:

| Verb and path | Result |
| --- | --- |
| `POST /changesets` | Validate operations and ancestry, atomically store bytes and immutable changeset; 201 new, 200 identical |
| `GET /changesets` | List recent records including ancestry, operations, derived validation and approvals |
| `GET /changesets/{id}` | Fetch immutable descriptor and related validation |
| `GET /changesets/{id}/tree` | Verify and list canonical tree manifest |
| `GET /objects/{id}` | Verify stored digest, restrict reads to the repository's reachable objects, return canonical base64 |
| `POST /changesets/{id}/approve` | Persist authenticated human owner approval |
| `GET /refs` | List current reference heads and generations |
| `PUT /refs/{name}` | Conditional reference advancement requiring validation and owner approval according to repository policy |

Write body example for `POST /changesets`:

```json
{
  "apiVersion": 1,
  "parents": [],
  "message": "Add workspace note",
  "operations": [
    {
      "kind": "PUT",
      "path": "docs/note.txt",
      "dataBase64": "SGVsbG8gRGV2SHVi"
    }
  ]
}
```

A new reference is created by `PUT /refs/main` with `{"changesetId":"<64-hex-ID>","expectedGeneration":null}` after review approval. An existing reference requires its last-read generation. Changesets can be submitted and reviewed without calling that endpoint.

## Authorization, safety and limits

Agent tokens are hashed, checked for expiry/revocation and repository ownership, and must have `changesets:read` or `changesets:write` scope. Approvals and reference writes require the authenticated administrator; browser-origin protection applies to mutation requests without a bearer token. Object reads are checked against history of that repository. Paths reject traversal, backslashes and absolute paths. File payloads are limited to 256 KiB each, at most 200 operations and 8 parents; current tree manifest limit is 10,000 paths / 4 MiB.

A successful `SourceValidation` means **manifest integrity, ancestry and input-shape validation only**. It does **not** mean that untrusted source files were compiled, scanned for vulnerabilities, tested, sandboxed or approved by a human. Reference advancement is gated by explicit owner approval when required.

## Trade-offs and roadmap

PostgreSQL stores blobs directly for transactional simplicity and deterministic deployment; an external immutable object store can later implement the same hash/byte contract, with a verified availability phase before references are exposed. Current changesets are persisted synchronously; expensive executable validation must be handed to persistent background workers using outbox delivery. The v1 API limits payload size; streaming/multipart upload, garbage collection, quota enforcement, resilient multi-region replication, conflict-aware multi-parent merge, branch protection, object reachability acceleration and a Git wire-format adapter are later milestones, **not** hidden v1 capabilities.

The existing PR integration tests remain mandatory so that migration does not break queue admission, outbox retry or human approval. Native integration tests run against real PostgreSQL, checking immutability, deterministic content hashes, ancestry, concurrent branchless changes, authorization and generation CAS. The production build and HTTP startup remain required CI gates.
